# M5 云端时序参考核对（2026-10-16）

M5 在用户提供的 Vivado 2025.1、ZU15EG-2、3.333 ns 独立 OOC 实现中满足已约束内部时序。云端已完成 RapidWright 参考图重建及 M4/M5 各 20 条导出建立路径的逐项对照。此次只新增分析工具，Chisel、RTL、Windows 流程及此前发布的 M5 包均未修改。

## 实测对比

| Vivado routed 结果 | M4 | M5 |
|---|---:|---:|
| 建立 WNS / ns | +0.346 | +0.477 |
| 保持 WHS / ns | +0.042 | +0.036 |
| TNS / THS | 0 / 0 | 0 / 0 |
| CLB LUT（含存储） | 7754 | 7816 |
| FF | 6309 | 6463 |
| RAMB36E2 | 2 | 2 |
| DSP48E2 | 6 | 6 |

M5 增加 62 LUT、154 FF，建立裕量增加 131 ps；2 个 BRAM 和 6 个 DSP 保持不变。12188 个需布线网络全部完成，布线错误为 0；13206 个建立/保持检查端点，无无时钟或未约束内部端点。上传的全部 output-sha256 项已验证，输入 RTL SHA 与已交付的 M5 一致。

最差路径由 M4 的 `unit/state_reg[1] → BRAM 写地址` 转为 M5 的 `unit/r32/result_reg[25] → unit/response_data_reg[49]`。M5 此路径数据延迟 2.836 ns，其中逻辑 0.890 ns、布线 1.946 ns，8 级 LUT。RAM 写入切分已使旧瓶颈退出最差位置；下一步应关注浮点结果打包和输入重编码。

## 云端参考模型的实测误差

RapidWright 2026.1.1-beta 使用本次 routed.dcp、同名可读 EDIF 和 6 份 DSP 延迟表。保留上游 DSP 目录字段兼容补丁的记录，不改写第三方 JAR。

| 导出的 20 条路径 | M4 | M5 |
|---|---:|---:|
| 匹配成功 | 20/20 | 20/20 |
| Q→D 延迟平均绝对差 / ns | 0.126890 | 0.050240 |
| 最大低估 / ns | 0.231200 | 0.120500 |
| 最大高估 / ns | 0.102500 | 0.128300 |

比较扣除了 Vivado 报告的发射时钟到输出延迟，BRAM 使用报告中的实际 DOUT 位，不假设它具有普通 FF 的 Q 引脚。参考模型求同一对引脚间的最长路径，具体路径可能不同。误差只覆盖导出的 20 条关键路径，不代表所有路径的误差上限。没有按 M5 数据拟合模型，也没有建立可用于新布线的误差保证。

M5 参考图含 83990 个顶点、107661 条边，未检测到环。全图参考最长延迟 2.817200 ns，位于 `unit/request_b_reg[20]/Q → unit/rb_reg[29]/D`。它与 Vivado 最差建立路径不同：参考图不能直接提供实际 WNS、器件 Fmax 或保持结论。

六份 DSP 表各 91 条记录，与 M4 的对应延迟表内容一致。表中数据和图中的 DSP 逻辑边数量不证明所有 DSP 内部寄存器间弧均已覆盖。

## 固定布线的周期预算

以下只用 `新裕量 = 0.477 + 新周期 - 3.333`，保持现有数据路径、建立检查和时钟假设，不重新综合、布局或布线。

| 假设频率 / MHz | 估算建立裕量 / ns |
|---:|---:|
| 300 | +0.477333 |
| 333.333 | +0.144003 |
| 350 | +0.001143 |
| 400 | -0.356000 |
| 500 | -0.856000 |

350 MHz 几乎无裕量，不应作为稳定运行承诺；500 MHz 仍需切分长链。缩短周期没有重新检查脉宽、保持或实际时钟树。

## 后续筛选流程

1. 复用本次结果作为物理基线；不要求用户仅为试频反复运行 Vivado。
2. 修改前先按路径选择切分点，优先考虑舍入结果的格式选择/IEEE 解码/NaN 规范化与响应选择之间的边界，以及输入重编码中的前导零和指数处理。
3. 修改后在云端用 Chisel/Mill 生成、独立数值回归、Yosys 资源和 FF 间组合链检查筛选。验证新增阶段的 flush、背压和标志传递。
4. 已有 DCP 的 RapidWright 数据用于定位和估算布线代价，不能作为修改后 RTL 的实现结果。候选通过上述检查且预期收益明确后，再合并一次本地 Vivado 验证。

本次完成的是基于真实布线的静态参考分析，没有生成 SDF，也没有进行新的带延迟门级事件仿真。当前 OOC 仍缺 HD.CLK_SRC、实际 BUFG/MMCM/顶层时钟树及主机 IO 约束，不构成 CPU/板级时序签核。
